# 三个政策官网采集验证技术方案

## 1. 建设目标

针对以下三个公开官网开展低频、合规的采集可行性验证，为后续正式连接器开发提供依据。

| 来源 ID | 来源 | 验证入口 | 重点信息 |
| --- | --- | --- | --- |
| `sc-jxt-notices` | 四川省经济和信息化厅 | `https://jxt.sc.gov.cn/scjxt/wjfb/common_list.shtml` | 资金申报、项目申报、需求征集、政策文件、名单公示 |
| `sc-kjt-notices` | 四川省科学技术厅 | `https://kjt.sc.gov.cn/kjt/gstz/newschild.shtml` | 科技项目申报、需求征集、揭榜挂帅、组织申报通知 |
| `most-service-notices` | 国家科技管理信息系统 | `https://service.most.gov.cn/kjjh_tztg_all/` | 专项名称、通知标题、发布日期、公开受理时间、官方入口 |

本阶段只完成访问验证、样本解析和连接器设计，不写生产数据库、不启用定时采集、不接入前端和推送链路。

### 实施状态（2026-09-18）

- 已完成三个来源的首轮低频验证、来源卡、结构化样本、最小 HTML 夹具和解析测试。
- 已实现统一采集引擎 `scripts/policy_source_crawler.py` 和统一命令入口 `scripts/crawl_policy_source.py`。
- 已额外采集三个来源前 10 页，共 30 个列表页、400 条去重详情，纯文本正文解析成功 400 条、失败 0 条。
- 四川省科技厅已支持普通通知、政策文件两套已知模板，并提供通用正文规则兜底。
- 批量采集使用 0.2 秒间隔，属于后续功能覆盖验证，不替代本方案规定的 60 秒低频验证和第二次真实运行。

> 省科技厅在任务截图中写作 `newchild.shtml`，任务书中为 `newschild.shtml`。实施时应将两者作为入口校验项，以实际返回有效列表的官方地址为准，并在来源卡中记录差异。

## 2. 当前阶段定位

本工作区是独立的本地证据收集项目，不属于 `news-agent-web` 的前端开发，也不作为正式爬虫项目直接合并。

当前阶段允许产出：

- 来源访问证据和来源卡；
- 结构化列表、详情样本；
- 可手动运行的低频验证探针；
- 最小公开 HTML 夹具；
- 针对固定夹具的解析测试；
- 两次真实运行的新增、重复、更新、失效和失败记录。

当前阶段不进行：

- 正式采集器注册；
- 生产数据库写入或迁移；
- 定时任务和任务队列接入；
- 搜索、阅读端和推送接入；
- 登录后页面、验证码或访问控制绕过；
- 最终连接器架构定型。

## 3. 总体流程

```text
来源配置
   ↓
访问预检
robots、HTTP 状态、重定向、响应大小、页面形态
   ↓
低频请求
列表页 → 10 条列表样本 → 3 条公开详情
   ↓
来源解析器
标题、日期、正文、附件、办理入口、发布主体
   ↓
标准化输出
RawFeedItem 兼容结构 + metadata + 字段证据
   ↓
来源卡、样本、响应哈希、最小 HTML 夹具
   ↓
固定夹具单元测试和第二次真实运行
```

验证代码采用“通用采集引擎 + 每站分页配置 + 每站解析器”。网络请求、解析和证据落盘分离；站点解析保持纯函数，以便最终方案确定后选择性迁移。

```text
crawl_policy_source.py
        ↓ 选择来源
policy_source_crawler.py
        ↓ 调用来源配置
分页 URL + 列表解析器 + 详情解析器
        ↓
lists.json + details.json + 原始 HTML + summary.json
```

## 4. 来源采集策略

| 来源 | 建议策略 | 列表处理 | 详情处理 | 初始频率 |
| --- | --- | --- | --- | --- |
| 四川省经信厅 | HTTP 直采 | 服务端 HTML 解析 | 提取正文、附件及公开办理链接 | 每日 2 次 |
| 四川省科技厅 | HTTP 直采 | 服务端 HTML 解析 | 提取正文、附件及申报入口 | 每日 2 次 |
| 国家科技管理信息系统 | 公开页面直采，必要时解析公开接口或 iframe | 提取专项、标题、日期和公开时间 | 只访问无需登录的公开页面 | 每日 1 次 |

统一访问要求：

- 使用如实、固定的 User-Agent，并提供项目标识或联系信息。
- 单站单线程，列表页和详情页请求间隔不少于 60 秒。
- 首次验证每站最多请求 1 次 `robots.txt`、1 次列表页、3 次详情页。
- 不携带登录凭证、Cookie 或个人信息。
- 不处理验证码，不绕过 403、412、429、登录提示或动态挑战。
- 需要登录或带实名水印的指南正文不采集，只保存公开标题、日期、公开时间和官方入口。

## 5. 数据结构

列表阶段输出：

```json
{
  "source_id": "sc-jxt-notices",
  "external_id": "sha256:canonical_url",
  "title": "官方原标题",
  "url": "https://...",
  "published_at": "2026-09-16T00:00:00+08:00",
  "content": null,
  "metadata": {
    "issuer": null,
    "source_level": "province",
    "department_line": "industry",
    "published_at_evidence": "列表日期文本及 DOM 定位",
    "collected_at": "2026-09-16T10:00:00+08:00"
  }
}
```

详情阶段在 `metadata` 中补充：

- `issuer`：源站明确给出的发布主体；
- `attachments`：公开附件名称和官方链接；
- `application_links`：正文明确给出的办理入口及是否需要登录；
- `deadline_text`：页面中明确出现的截止时间原文；
- `field_evidence`：日期、主体、期限等字段的文本或 DOM 证据。

日期、发布主体和截止时间必须来自源站明确内容。没有提供时保留 `null`，不得根据 URL、年份或采集时间推测。

## 6. 增量与去重

- **主去重键**：规范化后的详情 URL 计算 SHA-256，作为 `external_id`。
- **辅助去重键**：`source_id + 标题 + 发布日期`，用于识别 URL 变化或重复发布。
- **内容指纹**：对清洗后的标题、正文、附件列表计算 `content_hash`。
- **新增**：本次出现、历史不存在的 `external_id`。
- **重复**：`external_id` 和 `content_hash` 均未变化。
- **更新**：`external_id` 相同，但正文、日期、附件或办理入口发生变化。
- **失效**：原条目详情返回 404 或连续多次无法访问。单次超时不直接判定失效。

第二次真实运行与第一次至少间隔 1 小时，并输出新增、重复、更新、失效和解析失败数量。

## 7. 失败处理

| 情况 | 处理方式 |
| --- | --- |
| robots 明确禁止 | 停止访问对应路径并记录证据 |
| 403、412、验证码、登录挑战 | 不重试、不切换代理，标记为受限 |
| 429 | 停止该站本轮验证，记录限流 |
| 连接超时、5xx | 按 60 秒、5 分钟、30 分钟退避，最多 3 次 |
| HTML 结构变化 | 保留响应哈希，标记解析失败，不输出不完整数据 |
| 正文需登录 | 只保留公开列表字段和官方入口 |
| 日期、附件不存在 | 输出 `null` 或空数组，记录“源站未提供” |

必须区分“源站没有字段”“解析器没有找到字段”和“页面访问失败”。

## 9. 测试范围

每个来源至少覆盖：

1. 列表页解析 10 条记录；
2. 详情正文不混入导航和页脚；
3. 相对链接规范化；
4. 日期缺失时保持 `null`；
5. 无附件时输出空数组；
6. 附件名称和 URL 正确配对；
7. 重复运行能够识别重复；
8. 相同 URL 内容变化时识别更新；
9. HTML 结构变化时记录解析失败；
10. 登录或限制页面不被当成正文。

截至 2026-09-18 已有 17 项离线测试通过。现有测试覆盖上述主要解析路径，但“主发布日期缺失保持 `null`”仍需增加独立用例；第二次真实运行的增量、更新和失效分类也尚未对三个来源全部完成。

## 10. 交付与迁移

每个官网交付一张来源卡、10 条列表样本、至少 3 条详情样本、最小 HTML 夹具、解析测试、两次真实运行记录和正式接入建议。

```text
本地证据收集分支
    ↓
来源可用性和字段评审
    ↓
确定正式连接器方案
    ↓
在后端仓库新建实现分支
    ↓
选择性迁移已验证的解析逻辑、字段定义和测试夹具
```

不得将整个调研仓库直接作为正式实现合并。只有来源卡、样本、夹具、测试和两次运行证据齐全的来源，才进入正式连接器设计与审核阶段。
